# Integrating the selector processor into your project

## Layout

```
selector-annotation/
├── pom.xml                  aggregator (com.example:selector-parent)
├── selector-processor/      the annotation + processor — STANDALONE, no <parent>
├── selector-example/        a worked example: annotated models + a runnable demo
└── selector-lombok-example/ the same, with Lombok-generated getters, to prove that path works
```

`selector-processor` deliberately declares no `<parent>`, so you can copy the directory into
another repository, or `mvn deploy` it, without dragging this aggregator along. The aggregator
lists it as a module only so a root build compiles both in order.

Build and run everything:

```bash
mvn clean install
```

Then run the demo (or just run `DemoUsage` from the IDE):

```bash
java -cp selector-example/target/classes com.example.payments.demo.DemoUsage
```

Targets **Java 17**. The processor has no third-party dependencies — it emits source using only
the JDK's `javax.annotation.processing` / `javax.lang.model` APIs.

---

## What you need to do in your real project

### 1. Get the processor into your build

- **In-repo (simplest to start):** copy the `selector-processor` directory into your repository
  and add `<module>selector-processor</module>` to your aggregator. Change the `groupId` /
  `artifactId` to your conventions. Because it has no parent, nothing else needs changing.
- **Shared across repos:** `mvn deploy` it to your internal Artifactory/Nexus and depend on it
  by GAV. Worth doing once more than one service wants it.

### 2. Wire up the module that holds your API models

Copy the build configuration from [`selector-example/pom.xml`](selector-example/pom.xml):

- add the processor as a **`provided` dependency** — this makes the `@GenerateSelector` symbol
  resolve when compiling your source;
- add it to **`annotationProcessorPaths`** — this actually runs the processor, and keeps it off
  your runtime classpath.

Both entries are needed. `annotationProcessorPaths` sets `-processorpath`, which is separate
from the compile classpath, so the annotation symbol still needs the `provided` dependency.

No compiler arguments are required. Recursion follows whatever types your model references, so
models spread across packages need no configuration — see
[Bounding the recursion](#bounding-the-recursion) for the one case where you might want to
restrict it.

### 3. Annotate your root type(s)

Put `@GenerateSelector` on the aggregate roots you navigate from — the payment, the payee, the
message envelope. You do **not** annotate the nested types; recursion covers them. You can
annotate several roots; shared nested types are still generated once.

### 4. Build

`mvn clean compile`. Selectors appear under `target/generated-sources/annotations/`. They are
regenerated every build — **do not commit them**, and keep `target/` git-ignored.

### 5. IntelliJ

- Settings → Build, Execution, Deployment → Compiler → Annotation Processors →
  tick **Enable annotation processing**.
- After a build, IntelliJ marks `target/generated-sources/annotations` as a generated sources
  root automatically. If it doesn't, right-click it → Mark Directory as → Generated Sources Root.

### 6. Use at call sites

```java
String bic = PaymentSelector.of(payment)
        .payee().agent().financialInstitution().bic();   // null-safe, one line
```

## How your models expose properties

This determines whether it works out of the box.

- **Plain getters** — hand-written, or generated by openapi-generator without Lombok. Works out
  of the box; this is the common case for API model objects.
- **Java records** — works out of the box. Record accessors are `bic()` rather than `getBic()`,
  so they are picked up by record component rather than by naming convention.
- **Lombok (`@Data` / `@Getter`)** — works, **provided Lombok is on `annotationProcessorPaths`
  ahead of this processor**. This is verified end to end by `selector-lombok-example`, against
  Lombok 1.18.40: `@Data` getters, `is`-style booleans, boxed primitives and recursion through
  non-annotated Lombok types all come out correctly.

  `lombok-mapstruct-binding` turned out **not** to be needed — listing `lombok` itself first on
  the processor path is sufficient. Add the binding only if you also use MapStruct.

  The failure mode is worth knowing because it is quiet: if Lombok is a plain dependency but
  *not* on `annotationProcessorPaths`, the build **succeeds** and you get a selector with only
  the terminal methods and no properties at all. The processor now emits a warning naming this
  as the likely cause, but it is a warning, not an error — so it will scroll past in CI.

If you're unsure which bucket your models fall in, generate against a single model first and
eyeball the generated selector — every property you expect should have a method.

## Rules the processor applies

**Becomes a selector method:** public, non-static, parameterless, non-void `getXxx()`; `isXxx()`
when the return type is `boolean`/`Boolean`; record component accessors. Inherited getters are
included. `getClass()` is excluded.

**Descended into** (returns a nested selector) when the property type is a declared class, record
or interface outside `java.* / javax.* / jakarta.*` — that is, any type of yours the model
references. Package layout is irrelevant unless you set a bound.

**Treated as a leaf** (returns the raw nullable value): everything else — enums, collections,
maps, `Optional`, dates, arrays, and primitives (boxed so they can be null).

**Naming** follows JavaBeans: `getBic() → bic()`, and an acronym keeps its case,
`getURL() → URL()`. A property whose name would be a Java keyword keeps its accessor name
instead — `getDefault()` stays `getDefault()`, because `default()` is not a legal method name.

**Nested model types** get a flattened selector name: an inner class `Envelope.Header` produces
`Envelope_HeaderSelector`, so it cannot collide with another `Header` in the same package.

**Generated source is fully qualified throughout.** It costs some readability but means the
emitted file cannot fail to compile because of an unimported or ambiguous simple name.

## Bounding the recursion

**By default there is no bound.** Recursion follows the types your model actually references,
wherever they live, stopping only at the leaf rules above (JDK types, enums, collections, arrays,
primitives). Package layout is irrelevant — `com.acme.payments.Payment` referencing
`com.acme.parties.Party` just works, with no configuration.

You only need a bound if a model references a **third-party type** you would rather treat as an
opaque value than generate a selector for. Two ways, most specific first:

1. **`@GenerateSelector("com.acme")`** — on the root, keeps generation to your own code;
2. **`-Aselector.basePackage=com.acme`** in `compilerArgs` — the same thing project-wide.

Each root carries its own bound through the recursion, so roots configured differently do not
interfere with each other.

## Other notes

- **Matching is on whole package segments**, so `com.acme.model` will not capture
  `com.acme.modelling`.
- **Collections**: per-element navigation into `List<Foo>` is intentionally out of scope. The
  selector navigates object graphs; it does not iterate them.
- **Cycles and diamonds** (`A → B → A`, or two properties of the same type) are handled — each
  type is generated exactly once.
- **Reserved names**: a property named `of`, `orNull`, `orElse` or `asOptional` is skipped, so it
  cannot clash with the terminal methods.
- **Generics**: type variables are erased in the generated source (`List<T>` becomes `List`),
  because the generated selector declares no type parameters to bind them to.
- **Covariant overrides**: where a subtype narrows a getter's return type, the most specific
  declaration wins.
- **Type-use annotations** on your models (`@NotBlank String getName()`) are stripped from the
  generated source rather than copied into it.
- **Spring Boot fat jar**: `provided` scope plus the processor path keep the annotation and
  processor out of your runtime jar; `spring-boot-maven-plugin` repackage excludes provided deps.
- **Gradle**: `annotationProcessor project(':selector-processor')` plus
  `compileOnly project(':selector-processor')`, and
  `options.compilerArgs << '-Aselector.basePackage=...'`.

## Tests

`selector-processor` has 71 tests, run with `mvn -pl selector-processor test`. They invoke a real
`javac` with the processor attached ([`SelectorCompilation`](selector-processor/src/test/java/com/example/selector/SelectorCompilation.java)),
then assert on both the emitted source and the compiled runtime behaviour:

- [`SelectorGenerationTest`](selector-processor/src/test/java/com/example/selector/SelectorGenerationTest.java)
  — which selectors exist and which methods they declare, over a deliberately messy fixture
  (primitives, enums, collections, arrays, a third-party type, an acronym getter, inherited
  getters, and a spread of methods that must not be mistaken for properties).
- [`SelectorNullSafetyTest`](selector-processor/src/test/java/com/example/selector/SelectorNullSafetyTest.java)
  — loads the compiled selectors and chains them for real: full graph, missing intermediate,
  null root, self-reference, two-type cycle, and the terminal methods.
- [`SelectorEdgeCaseTest`](selector-processor/src/test/java/com/example/selector/SelectorEdgeCaseTest.java)
  — records, interfaces, generics erasure, nested model types, keyword property names, covariant
  overrides, type-use annotations, misuse of the annotation (enum / annotation type both produce
  a clear compile error), base-package boundaries, and reserved-name clashes.

Several of these assert only that compilation *succeeds* — that is the point: each covers a case
that previously emitted Java which did not compile.
